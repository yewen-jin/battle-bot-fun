# Image generation brief — bot sprites + arena background

For running through Google Antigravity (or any image-generation tool that accepts an
input image + text prompt). Two deliverables: 24 bot sprites, 1 arena background.

## 1. Bot sprites

**Input:** one reference photo per bot in `sprites/source/<Bot>.jpg` or `.png`
(actually WebP bytes regardless of extension — Fandom serves WebP; most image
tools handle this fine, but rename/convert if yours is picky). Generated by
`image-scripts/4_images.py`.

**Output:** save each result to `media/bots/<slug>.png`, where `<slug>` is the bot's
name lowercased with spaces/punctuation replaced by hyphens (see the exact rule in
`media/bots/README.md`). Example: `Witch Doctor` → `media/bots/witch-doctor.png`.
Dropping a file in with the right name is the *only* wiring needed — `render.js`
picks it up automatically per-bot at runtime, falling back to a plain colored blob
for any bot without a file.

**Prompt** (tested and validated against the actual reference photos for Tombstone/Minotaur):

```
Turn this photo of a combat robot into simple, clean sprite art for a tiny 2D
game icon. Draw it in an axonometric / isometric 45-degree bird's-eye-view
perspective, as if looking down at the robot from above at an angle. Flat
color regions, bold 1-2px dark outline, no gradients, minimal shading.
Preserve the robot's actual recognizable silhouette and color scheme from the
photo. Square image, robot centered and filling most of the frame, plain
white or transparent background. Must read clearly as a small icon at 32x32
pixels — keep shapes simple and blocky rather than finely detailed, since it
will be scaled down significantly and then upscaled with nearest-neighbor
(no smoothing), so any fine detail will just turn to noise.
```

**Technical constraints to hold non-negotiable** (from `CLAUDE.md`/`media/bots/README.md`):
- Roughly square canvas, transparent (or flat, easily-removable) background
- Robot centered, filling most of the frame
- Simple/blocky enough to survive being drawn into a 14×14 world-unit box and
  upscaled 8× with nearest-neighbor (no anti-aliasing) — ornate detail disappears
  at that scale, flat shapes and bold silhouettes read best
- Consistent art style across all 24, so the roster doesn't look mismatched

## 2. Arena background

**Input:** none — generate from the text description below (no reference photo needed,
though a real BattleBox photo could be used as a style reference if you want one).

**Output:** save as `media/arena.png`. (Wiring this into `render.js` as the background
— currently a flat fill color — is a separate follow-up code change, not done yet.)

**World geometry it must match** (from `PRD.md` Section 2 — get this right or the
painted arena won't line up with where bots actually bounce):
- World is 160×90 units, floor at `y = 78`, walls at `x = 8` and `x = 152`
- So there's an 8-unit margin on each side before the walls, and a 12-unit strip
  below the floor line (down to `y = 90`) — that's under-the-floor/base structure,
  not part of the play area
- Aspect ratio: 160:90 (16:9) — generate at that ratio, e.g. 1600×900 or 1920×1080

**Prompt:**

```
A pixel-art / flat vector illustration of an empty BattleBots-style combat
robot arena, viewed from an axonometric / isometric 45-degree bird's-eye
angle — the same camera angle as looking down at a tabletop battle box from
above and to the side. Steel floor with visible wear/scorch marks, thick
metal walls on the left and right sides (bulletproof polycarbonate + steel
frame, industrial look), no robots or people in the shot — just the empty
arena floor and walls, ready for a fight. Flat color regions, bold dark
outlines, minimal gradients, matching a simple 8-color retro pixel-art
palette. 16:9 aspect ratio. No text, no logos, no UI elements.
```

## Notes

- Both prompts were designed to match this project's existing render style: flat
  colors, dark outlines, no gradients, an 8-colour palette (`CONFIG.palette` in
  `physics.js`) — if the generated output leans photorealistic or heavily shaded,
  ask for "flatter, fewer gradients, more like a simple icon" as a follow-up edit.
- If you generate sprites with a visible background instead of transparent, that's
  fine as long as it's a single flat color that's easy to key out (e.g. pure white
  or pure magenta) — I can strip it in code afterward if needed.
